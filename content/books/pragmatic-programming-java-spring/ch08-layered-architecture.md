## 핵심 아이디어

레이어드 아키텍처는 단순하고 직관적이어서 입문 자료에 가장 많이 등장하고, 그만큼 가장 많이
잘못 쓰인다. 무너지는 원인은 설계의 출발점이다. DB 엔티티에서 시작하거나 API 엔드포인트에서
시작하면 레이어를 나눠도 구조는 따라오지 않는다. 바꿔야 할 것은 인지 모델이다.

## 요점

- 레이어드 아키텍처는 애플리케이션을 레이어로 나누고 각 레이어에 역할을 정하는 구조다. 최소 조건이 있다.
- DB 엔티티 우선 접근과 API 엔드포인트 우선 접근이 각각 문제를 만든다.
- 개선의 출발점은 인지 모델 변경이다. 무엇을 먼저 떠올리는지가 구조를 결정한다.
- JPA와의 결합, 웹 프레임워크와의 결합을 끊어야 아키텍처가 진화할 수 있다.
- 레이어를 나눠도 빈약한 도메인 모델은 남는다. 구조가 설계를 보장하지 않는다.

## 실천 아이템

- [ ] 새 기능을 설계할 때 DB 테이블이나 API 엔드포인트가 아니라 도메인에서 시작한다.
- [ ] 도메인 클래스에 JPA 애너테이션과 웹 프레임워크 의존이 섞여 있는지 확인한다.

## 용어

레이어드 아키텍처
: 애플리케이션을 프레젠테이션·비즈니스·인프라스트럭처 같은 레이어로 나누고 각 레이어에 역할을 주는 구조.

빈약한 도메인 모델 (anemic domain model)
: 데이터만 갖고 행동이 없는 도메인 객체로 구성된 모델.
