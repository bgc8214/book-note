## 핵심 아이디어

기능이 다른 서비스라도 비기능적 요구사항은 같을 수 있다. 캐싱도 인증도 각 서비스가 따로
구현하면 작업이 중복되고, 부족한 엔지니어링 리소스가 흩어져 오류가 생긴다. 공통 기능을
한곳으로 모으는 것이 기능적 분할의 다른 얼굴이다.

## 요점

- 기능이 다른 서비스도 같은 비기능적 요구사항을 공유할 수 있고, 각자 구현하면 중복과 오류가 생긴다.
- API 게이트웨이는 상태 비저장 경량 웹 서비스로 보안, 오류 검사, 성능과 가용성, 로깅을 처리한다.
- 서비스 메시(사이드카)는 각 호스트가 자체 사이드카를 가지므로 어떤 서비스도 남의 몫을 가져가지 못한다.
- 공통 기능을 라이브러리로 배포하면 업데이트 시점을 사용자가 쥐게 되어, 버그가 남은 옛 버전이 계속 돌아간다.
- 통신 패러다임마다 대가가 다르다. REST는 배우기 쉽고 캐시 가능하며, gRPC는 리소스 최적화용 바이너리, GraphQL은 정확한 요청이 가능하지만 복잡하고 보안 설정이 어렵다.

## 실천 아이템

- [ ] 공통 기능을 라이브러리로 낼지 서비스로 낼지, 버전 통제권과 독립 확장 가능성을 기준으로 비교해 적어본다.
- [ ] REST를 쓸 때 캐시 가능한 리소스를 명시적으로 선언한다.

## 용어

API 게이트웨이
: 여러 서비스에 걸친 공통 기능(보안·오류 검사·성능·로깅)을 처리하는 상태 비저장 경량 웹 서비스.

사이드카 패턴 / 서비스 메시
: 각 호스트에 붙는 프록시가 공통 관심사를 처리하는 패턴. 이스티오가 대표 구현이다.

메타데이터 서비스
: 여러 구성 요소가 함께 쓰는 데이터를 모아 두어 네트워크 트래픽을 줄이는 서비스.

서비스 디스커버리
: 클라이언트가 사용 가능한 서비스 호스트를 찾아내는 장치.
