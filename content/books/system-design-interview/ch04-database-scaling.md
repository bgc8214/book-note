## 핵심 아이디어

상태 저장 서비스는 상태 비저장 서비스보다 설계가 훨씬 복잡하고 오류도 잦다. 그래서 좋은
설계는 서비스를 상태 비저장으로 유지하고 상태는 공유 저장 서비스로 밀어낸다. 저장 계층의
선택과 확장은 그 밀어낸 복잡성을 어디서 감당할지 정하는 일이다.

## 요점

- 상태 저장 서비스는 일관성 보장 메커니즘과 복제가 필요해 상태 비저장보다 훨씬 복잡하다.
- 저장 기술은 데이터베이스(SQL·NoSQL), 문서, 그래프, 파일·블록·객체 스토리지로 나뉜다. 데이터베이스만 후보로 두지 않는다.
- 복제 기술에는 단일 리더, 다중 리더, 리더 없는 방식이 있다.
- 데이터베이스가 단일 호스트의 저장 용량을 넘으면 샤딩이 필요하다.
- 데이터베이스 쓰기는 비싸고 확장이 어렵다. 이벤트를 집계하면 쓰기 빈도를 줄일 수 있다.
- 캐시 전략마다 트레이드오프가 다르고, 개인 데이터는 캐시하지 않는다.

## 실천 아이템

- [ ] 저장 방식을 정할 때 데이터베이스와 파일·블록·객체 스토리지를 함께 후보에 올려 비교한다.
- [ ] 쓰기가 많은 설계에서는 이벤트 집계로 쓰기 빈도를 줄일 수 있는지 먼저 확인한다.

## 용어

샤딩 (sharding)
: 데이터를 여러 호스트에 나눠 저장하는 것. 단일 호스트의 저장 용량을 넘을 때 필요해진다.

이벤트 집계
: 개별 쓰기를 모아 한 번에 기록해 데이터베이스 쓰기 빈도를 줄이는 기법.

람다 아키텍처 (lambda architecture)
: 같은 데이터를 배치와 스트리밍 파이프라인으로 나란히 처리해 두 방식의 장점을 함께 얻는 구조.

비정규화 (denormalization)
: 읽기 지연과 쿼리 복잡도를 줄이기 위해 중복을 허용하는 것. 일관성·쓰기 속도·저장 공간을 대가로 낸다.

캐시 어사이드 (cache aside)
: 애플리케이션이 캐시를 먼저 확인하고 없으면 DB를 읽는 전략. 읽기 위주 부하에 적합하지만 캐시 미스가 느리다.

지연 쓰기 캐시 (write-behind)
: 갱신된 데이터를 주기적으로 DB에 플러시하는 캐시. 장애 시 데이터 손실을 막으려면 높은 가용성이 필요하다.

캐시 워밍 (cache warming)
: 첫 사용자도 캐시 이점을 받도록 미리 캐시를 채워두는 것.
